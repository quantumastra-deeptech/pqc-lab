        MODULE 05

        TLS Handshakes, Certificates & PKI.
        Transport overhead, packet fragmentation, and CA readiness.

        Transport-layer migration impacts network packet budgets. Classical certificates (~1.2 KB) fit inside a single TCP Initial Window (IW10); PQC certificates span multiple TCP packets, risking latency amplification.

        CLASSICAL TLS 1.3 (ECDHE-RSA) HNDL AT RISK

        Session keys established via ECDH P-256 (65 bytes). Certificate chain signed with RSA-2048 (~2 KB). Handshake comfortably fits in standard TCP MSS (1,460 bytes).

        • ClientHello: Supported ciphersuites, 65-byte ECDH KeyShare (1 Packet)
        • ServerHello: 65-byte ECDH KeyShare, EncryptedExtensions (1 Packet)
        • Certificate: RSA-2048 leaf + intermediate certs (~2.4 KB, 2 Packets)
        • Finished: 1-RTT connection established. Vulnerable to retroactive decryption.
        HYBRID & PQC TLS 1.3 (X25519MLKEM768) QUANTUM SAFE

        Key exchange combines X25519 (32 B) + ML-KEM-768 (1,184 B). Certificate chain signed with ML-DSA-65 (~8-12 KB). Requires connection pooling to mitigate TCP fragmentation.

        • ClientHello: Hybrid KeyShare: X25519 (32 B) + ML-KEM (1,184 B) (Spans 1-2 Packets)
        • ServerHello: ML-KEM Ciphertext (1,088 B) + EncryptedExtensions (Spans 2 Packets)
        • Certificate: ML-DSA-65 Certificate Chain (~10.5 KB, Spans 7-8 Packets!)
        • Mitigation: Use Hybrid KEM for transport first; retain classical certs during transition.

        * Notice: Browser WebCrypto execution simulates application-level envelope cryptography. The actual network transport TLS connection is negotiated directly between your browser engine and the hosting CDN/edge server.

        MODULE 08

        Database & Data Migration Strategy.
        Key rewrapping versus bulk re-encryption, and historical signature retention.

        Do not rewrite petabytes of transactional tables when only the protecting Key Encryption Keys (KEKs) require migration. Symmetric AES-256 data remains quantum-resistant.

        1. ENVELOPE ENCRYPTION REWRAPPING (RECOMMENDED) ZERO DOWNTIME

        In a modern banking database, table records are encrypted with local Data Encryption Keys (DEKs) using AES-256-GCM. The DEKs are encrypted (wrapped) by a master Key Encryption Key (KEK).

        Migration Path: Un-wrap the DEK using the classical RSA-OAEP KEK, and immediately re-wrap it using ML-KEM-768. The millions of transactional customer records remain untouched in storage!

        2. HISTORICAL SIGNATURE PRESERVATION (RFC 3161) LEGAL COMPLIANCE

        Past payments signed with RSA-2048 cannot be retroactively re-signed by customers who approved them years ago.

        Migration Path: Bundle historical transactions into Merkle trees and notarize the Merkle roots using a post-quantum ML-DSA-65 timestamping authority (RFC 3161 Evidence Records). This establishes non-repudiation proof that the transaction existed before RSA was cracked.
